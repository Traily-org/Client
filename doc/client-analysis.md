## 1. Résumé

- Le repo est au stade **squelette** : un projet `create-expo-app` (SDK 57) réorganisé, trois écrans placeholder et un thème défini mais non branché. Aucune fonctionnalité du backlog n'est livrée sur `develop`.
- Le seul travail fonctionnel est la **carte MapLibre** de `feat/map` (non mergée), de bonne facture : trois fonds de carte, tracé de démo, écran crédits.
- La **CI** existe sur une branche non mergée (`chore/frontend-ci`) et n'a jamais tourné. En l'état, **tous ses jobs échoueraient**, pour deux causes identifiées et simples à corriger.
- Un **environnement Docker de dev** (`chore/frontend-docker`) attend lui aussi une PR. Il ne crée aucun conflit.
- Trois **problèmes runtime** : splash natif jamais masqué et dossier `assets/` absent (toutes les branches), styles NativeWind très probablement non chargés (corrigé sur `feat/map` seulement).
- `main` ne compile pas. `develop` n'affiche aucune route (layout racine sans `<Slot/>`), ce que corrige `feat/map`.
- Écarts avec le Quality Plan : structure par feature plutôt que par couches, Vitest plutôt que Jest, et ni client API, ni store, ni stockage sécurisé en place.

## 2. Méthode

- Lecture de tous les fichiers suivis par git sur chaque branche. Historique via `git log --all --graph`, comparaison des arbres (`git rev-parse <branche>^{tree}`), fusion simulée en mémoire (`git merge-tree --write-tree`).
- Côté GitHub (`gh`) : PR, exécutions de workflows, rulesets de branches.
- Chaque branche a été exportée hors du working tree (`git archive`), installée avec `pnpm install --frozen-lockfile` comme en CI, puis vérifiée avec `tsc --noEmit`, ESLint, `prettier --check` et `vitest run`. La fusion `chore/frontend-ci` + `feat/map` a été reconstituée (conflits résolus, lockfile régénéré), vérifiée de la même façon, puis passée à `expo-doctor`.
- Environnement : Windows 11, Node 22.12.0, pnpm 10.32.1 (10.13.1 quand `packageManager` l'impose).
- Aucune exécution sur simulateur ni sur device. Les comportements runtime sont déduits du code et de la documentation des API, et signalés comme tels.
- Mise à jour du 09/10 : lecture des nouveaux commits et fusions simulées (`git merge-tree`), sans réinstallation ni nouvelle vérification outillée.

## 10. Qualité générale du code

- **Volume** : environ 210 lignes sous `app/` et `src/` sur `develop` (dont 104 pour `theme.ts`), et environ 750 lignes ajoutées par `feat/map` (composants, styles, écran crédits, scripts), hors JSON de style et lockfile.
- **Code hérité du template** (thème, hooks) : propre mais en partie inutilisé, avec des restes (`TabLayout`, `Fonts`, `BottomTabInset`…).
- **`feat/map`** : le meilleur code du repo. Il est lisible, les commentaires expliquent le _pourquoi_ (CORS, résolution du worker par Metro, zoom min, versions divergentes de `StyleSpecification`), la séparation natif/web est nette, l'effet web nettoie derrière lui (`map.remove()`), et le proxy fait des retries et ajoute des en-têtes de cache. Points faibles : couleurs codées en dur hors thème (en `StyleSheet` et en classes Tailwind arbitraires comme `bg-[#e0733f]` dans `MapModeSwitcher`), une exception pour une config manquante, des données de démo (point et tracé), aucun test alors que `getMapStyle` et `getAllAttributions` sont des fonctions pures faciles à tester, et des `Pressable` (marqueur, sélecteur de mode) sans libellé d'accessibilité.
- **Transverse** : aucun test, pas d'error boundary, textes en dur (pas d'i18n), accessibilité non traitée, typage strict respecté (les casts `as StyleSpecification` sont justifiés en commentaire).
- **Bilan** : base saine mais embryonnaire. La dette porte surtout sur la configuration et l'outillage, et elle est peu coûteuse à résorber maintenant, avant l'arrivée des features.

## 11. Environnement de développement : points d'attention

- **Node** : la CI utilise Node 22 ; Vitest 5 exige `^22.12.0 || ^24 || >=26`. Éviter Node 23.
- **pnpm** : `packageManager` fige la version (10.13.1) et pnpm bascule automatiquement dessus. Si `corepack` échoue avec « Cannot find matching keyid » (clés de signature obsolètes des anciens Node), installer pnpm globalement avec `npm i -g pnpm` ou mettre à jour corepack.
- **Typecheck local** : lancer `pnpm start` au moins une fois pour générer `expo-env.d.ts` et `.expo/types` (routes typées).
- **Windows** : garder le clone dans un chemin court (limite de 260 caractères dans `node_modules/.pnpm`) et utiliser des fins de ligne LF (P17).
- **Expo Go ou dev build** : Expo Go suffit tant qu'aucun module natif custom n'est ajouté. Dès `feat/map` (MapLibre), il faut un dev build (`pnpm expo run:android` / `run:ios`, ou un build EAS de développement). Les dossiers `/ios` et `/android` sont générés et ignorés par git (Continuous Native Generation).
- **Docker** (`chore/frontend-docker`) : `cp .env.example .env`, renseigner l'IP LAN, puis `docker compose up --build` ou `task docker:dev`. Pas besoin de Node ni de pnpm sur le poste. Metro écoute sur le port 8081 : en cas de conflit avec une autre stack locale (backend compris), changer le port publié d'un côté.
- **Variables d'environnement** : `traily-client/.env` avec `EXPO_PUBLIC_PM_TILES_URL` pour la carte, `REACT_NATIVE_PACKAGER_HOSTNAME` pour Docker, puis `EXPO_PUBLIC_API_URL`. Seul le préfixe `EXPO_PUBLIC_` est exposé au bundle, donc aucun secret dans ces variables.
- **GPS** : position simulée dans les simulateurs Xcode et Android Studio. Les tests réels de tracking en arrière-plan exigent un device (critères du backlog : 3 constructeurs Android).

## 12. Pour reprendre le développement front

1. Partir de `develop`, jamais de `main`.
2. Obtenir le merge de `chore/frontend-ci` (après P1 et P2), de `chore/frontend-docker` (après P21), puis de `feat/map`. Détail : sections « Branches » et « Recommandations » de [CLAUDE.md](../CLAUDE.md).
3. Corriger P3, P4 (si `feat/map` n'est pas encore mergée) et P7 avant d'évaluer quoi que ce soit visuellement sur device.
4. Créer `traily-client/.env` à partir de `.env.example` (complété avec `EXPO_PUBLIC_PM_TILES_URL`), puis préparer un dev build.
5. Poser les fondations (navigation, tokens, client API avec mocks, store, stratégie de tests) avant d'attaquer les features : [frontend-roadmap.md](frontend-roadmap.md).
6. Consulter la doc Expo **v57** pour toute API Expo ou Expo Router (`traily-client/AGENTS.md`).
